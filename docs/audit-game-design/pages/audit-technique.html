Terra Umbra : le moteur est solide, le contenu est prisonnier du code

Ce rapport porte sur l'API, la base de données, l'infrastructure, l'espace personnel, les campagnes et la table de jeu en direct. Il répond à une question précise : comment permettre aux administrateurs de faire vivre le compendium (ajouter des articles, les relier) sans passer par un développeur ?

Verdict. Il ne faut pas réécrire le site dans un autre langage. TypeScript, Fastify, PostgreSQL et Vue forment une base saine et moderne, et l'essentiel de la valeur (2 553 entrées de règles, le moteur de table en direct, les permissions MJ/joueur) y est déjà. Le vrai problème est architectural : le contenu du compendium et des règles est écrit dans le code source, sous forme de plus de 220 fichiers TypeScript empilés en couches de correctifs. Tant que ça reste vrai, aucun outil d'administration ne pourra être confortable. La priorité est donc de faire de la base de données la source de vérité du contenu, puis de brancher un vrai CMS dessus.

Faut-il changer de langage ?

Non. Voici les options sérieuses, et pourquoi elles ne valent pas une réécriture :

OptionCe qu'elle apporteraitCe qu'elle coûteraitAvis
Rester en TypeScript, restructurerGarde tout le moteur de règles, les tests et la connaissance accumuléeMigration du contenu vers la base, découpage en modulesrecommandé
PHP / Laravel + FilamentBack-office d'administration très rapide à produireRéécrire ~4 Mo de logique de règles et le temps réel ; deux langages pour une seule personnenon
Python / Django adminAdmin automatique sur les modèlesMême problème : le moteur de jeu est en TS et partagé avec le frontnon
Nuxt (Vue plein écran côté serveur)Pages d'articles indexables, partage de liens propreMigration progressive possible, pas obligatoireplus tard

L'argument décisif : le moteur de règles (apps/api/src/rules, 2,5 Mo de logique) doit tourner à la fois côté serveur (autorité sur les jets et les coûts) et côté client (aperçu dans le créateur de personnage). Seul TypeScript permet de partager ce code entre les deux. Le besoin « que les administrateurs puissent modifier le site » se règle avec un CMS branché sur la même base, pas avec un nouveau langage.

Le cœur du problème : le contenu vit dans le code

Au démarrage, loadCorpus() (lignes 2055 à 4108 de compendium.ts) reconstruit le compendium en empilant, dans un ordre précis :

  1. un manifeste manifest-v3.json et ses jeux de données compressés ;
  2. les articles « Moteur V4 », puis « Réalité V9 », qui écrasent les anciens articles de même identifiant ;
  3. des dizaines d'enrichissements éditoriaux (corporations, Pègre, PNJ, Vérité V7…) chargés depuis 221 modules TypeScript compendium-*.ts (compendium-realite-v9-corporations-payload-0.ts à -7, compendium-pnj-truth-civilians-06.ts à -16, etc.) ;
  4. 15 tables de correspondance d'identifiants de PNJ « résolus » ;
  5. un fichier manual-overrides.json ;
  6. enfin, les éditions faites dans l'éditeur web, stockées en base (compendium_article_edits) et appliquées par-dessus.

Conséquences concrètes :

  • Une édition en ligne peut être écrasée ou devenir orpheline lorsqu'un nouveau lot de code remplace l'article de base. L'API publique en témoigne déjà : "overrides":{"applied":1,"conflicts":9} et "databaseEdits":{"applied":33,"conflicts":1}.
  • Ajouter un article ou un PNJ exige un commit, une compilation et un déploiement. Un administrateur non développeur ne peut pas le faire.
  • Le démarrage de l'API recompile tout le corpus en mémoire (2 496 articles) et chaque modification de contenu fait grossir le bundle.
  • Les liens entre articles sont implicites (identifiants dans le texte, tables de « resolved ids ») : il n'existe pas de graphe de relations interrogeable, donc pas de rétroliens fiables.
  • Les règles de jeu suivent le même schéma : rules/truth/hunter-revision.ts (302 Ko), catalog-humain.ts (258 Ko), runtime-structure.ts (258 Ko), et des scripts check-*-revision.mjs lancés à chaque build.
Correctif structurel : faire une migration unique qui exécute loadCorpus() une dernière fois, écrit le résultat fusionné (éditions en base comprises) dans des tables normalisées, puis supprime les modules de contenu du code. À partir de là, la base de données est la seule source de vérité, et le code ne contient plus que de la logique.

Modèle de données proposé pour le contenu

content_entry      (id, type, slug, title, status, category, summary, body_blocks jsonb,
                    visibility, created_by, updated_by, published_at, version)
content_type       article | regle | talent | trait | objet | equipement | augmentation
                   | pnj | creature | lieu | organisation | glossaire
content_field      champs typés par type (coût PTV, accès V/SR/R, PA, quota, prérequis,
                   profil d'arme…) → JSON Schema par type, validé à l'écriture
content_relation   (from_id, to_id, kind)   kind = mentionne | prerequis | appartient_a
                   | membre_de | fabrique_par | voir_aussi | remplace
content_revision   (entry_id, version, snapshot, author, comment, created_at)
content_media      (id, entry_id, file, alt, credit, visibility)
taxonomy / tag     arbre de rubriques + étiquettes libres, gérés dans l'admin

Les talents, objets et PNJ deviennent des entrées typées avec des champs structurés au lieu de texte libre. C'est ce qui permettra à la fois d'éditer proprement, de générer des cartes imprimables et d'automatiser les règles sans réécrire de code (voir la section moteur de règles).

Le CMS pour les administrateurs

L'éditeur actuel (CompendiumEditorPage.vue, 1 815 lignes, routes /api/compendium/editor/*) sait déjà gérer brouillon, publication, médias, historique et rôles editor/admin. Il manque l'essentiel pour un usage quotidien : un modèle de contenu structuré et des relations. Deux voies réalistes :

A. Directus sur la même base PostgreSQLB. Back-office maison dans l'app Vue
PrincipeDirectus se branche sur les tables existantes et génère une interface d'admin complète (formulaires, relations, médias, rôles, révisions, API).Étendre l'éditeur actuel avec un éditeur de blocs, un sélecteur de relations et une vue de graphe.
Délai jusqu'à un usage confortable2 à 4 semaines (surtout la migration du contenu)2 à 4 mois
Relations, rétroliensNatifs (Many-to-Many, aperçu des éléments liés)À construire
Rôles et flux de validationNatifs, avec permissions par champÀ construire (le socle compendium_review_state existe)
Cohérence visuelle avec le siteInterface Directus, distincte du siteTotale
RisqueUn service de plus à héberger (Docker, ~300 Mo de RAM)Charge de développement continue

Recommandation : voie A pour le contenu éditorial (articles, PNJ, lieux, organisations, médias), et garder l'app Vue pour tout ce qui est « jeu » (création de personnage, campagnes, table). Payload CMS est une alternative en TypeScript si tu préfères un CMS dont tu peux modifier le code ; Directus a l'avantage de ne rien imposer au schéma.

Fonctions indispensables pour l'édition

  • Éditeur de blocs (paragraphe, tableau de règles, encadré MJ, exemple, citation, image) au lieu de JSON de sections.
  • Liens internes par autocomplétion : taper [[Vamp propose « Vampire », crée une relation mentionne et rend un lien qui survit au renommage.
  • Rétroliens (« Cet article est cité par… ») et détection des liens cassés à la publication.
  • Relations typées : un PNJ appartient à une organisation, un talent a des prérequis, un objet a un fabricant. L'admin choisit dans une liste au lieu d'écrire un identifiant.
  • Révisions et comparaison avec restauration (le socle compendium_article_edit_revisions existe).
  • Statuts brouillon → relecture → publié → archivé, et visibilité public / joueurs connectés / MJ seulement.
  • Import/export CSV ou JSON par type (talents, équipement) pour les corrections en masse dans un tableur.
  • Prévisualisation de l'article tel qu'il apparaîtra sur le site, et de la carte de talent imprimable.

Le moteur de règles

C'est la partie la plus aboutie et la plus précieuse du projet. Les jets sont tirés côté serveur avec crypto.randomInt, le serveur contrôle coûts, quotas, révélation et prérequis, et les suites de tests couvrent rejeu, falsification de sauvegarde et conflits de version. L'audit du 9 octobre recense 2 553 entrées et leur couverture.

Trois faiblesses :

  1. Les règles sont du code, pas des données. Chaque talent automatisé l'est par du code ad hoc (live-vampire.ts, live-frenzy.ts, lightning-*.ts, registered-power-state.ts…). Modifier un coût ou un bonus impose un développeur. Ça bloque l'évolution du game design.
  2. La couverture est faible en proportion : 263 talents humains sur 266 sont en « texte / activation assistée », 142 Exilés sur 184, 125 Extrals sur 162. Le serveur suit le coût et le quota, mais la table résout l'effet à la main.
  3. Les textes sont rédigés pour un humain, pas pour une machine : conditions, exceptions et « le MJ décide » sont dans la prose.
Proposition : standardiser chaque talent sous un gabarit structuré, qui sert à la fois au papier (carte lisible) et au moteur (effet exécutable). 
{
  "nom": "Faveur de la nuit",
  "cout": 1, "acces": "R", "activation": "passif",
  "declencheur": { "test": "furtivite", "contexte": "ombre_ou_obscurite" },
  "effet": [{ "type": "bonus_test", "valeur": 3 }],
  "quota": null,
  "texte_court": "+3 Furtivité dans l'ombre."
}
Avec une vingtaine de types d'effets (bonus au test, relance, réduction de dégâts, PA bonus, ressource +/-, état appliqué, contexte préparé, information demandée au MJ…), on couvre l'immense majorité des 1 187 talents de Vérité. Le reste garde un effet « narratif » explicite. Cette standardisation rejoint directement les recommandations de l'audit game design.

L'espace personnel

Route /account, portée par App.vue (1 185 lignes), qui sert aussi de coquille de l'application. Contenu : compte, personnages (CharactersPanel), fiches partagées avec moi, campagnes, dernière lecture, demande de statut MJ, et pour les admins la gestion des utilisateurs et le journal d'audit.

Ce qui fonctionne

  • Révisions de fiche avec restauration (/api/characters/:id/revisions), historique et journal du personnage.
  • Partage de fiche en lecture à des comptes nommés (character_sheet_readers), sans droit de mutation.
  • Favoris de personnages, galerie d'images, export PDF côté client (pdf-lib).
  • Import des fiches V1 (/api/characters/import-v1).

Les campagnes

Le périmètre fonctionnel est très riche, plus que la plupart des VTT commerciaux pour la préparation : membres et invitations, admissions avec messagerie, séances planifiées avec présences et invitations calendrier par e-mail, préparation de séance (scènes, effets), bibliothèque de préparation, PNJ de campagne (générateur canonique, portraits), bestiaire de campagne (générateur, équilibrage indicatif), récompenses par séance (XP, PTV, argent, Renommée, Corruption, équipement) avec garde anti-doublon, versions de personnage par séance.

Points forts techniques

  • Récompenses attribuées par lots, avec contrainte SQL qui interdit une récompense vide et un garde contre la double attribution.
  • Versions de personnage figées par séance (campaign_character_versions) : on peut savoir quelle fiche a joué quelle séance.
  • Projection publique des autres joueurs limitée (portrait, identité publique, camp, état de blessure) : bonne séparation de la vie privée.

La partie « en jeu »

La table (/campaigns/:id/play) et la fiche jouable (/characters/:id/play) reposent sur /api/campaigns/:id/play et /play/actions, avec les tables campaign_live_*, character_play_states et character_play_events.

Ce qui est remarquable

  • Le serveur fait autorité : jets, coûts en PA, quotas, révélation, Edge, consommation de munitions et charges.
  • Les jets sont rejouables et vérifiables (journal d'événements, détail du dé, explosion).
  • Contrôle de version optimiste (campaign_live_versions) contre les doubles clics et les conflits.
  • Résolutions occultes avec consentement ou défense de la cible, réactions (Gardien, Caendis, ripostes), effets avec horloges par round, activation ou scène.

Utilisation des compétences par les joueurs

Le panneau personnel propose Jets, États & PV, Pouvoirs et Équipement. Un jet se fait en choisissant une compétence, un bonus, la visibilité publique, et le serveur ajoute les bonus contextuels préparés. Ça marche, mais :

  • le joueur doit savoir quel bonus contextuel s'applique ; avec 3 à 10 talents à +2/+3 conditionnels, le serveur ne peut pas deviner le contexte. Il faut afficher, au moment du jet, la liste des bonus éligibles cochables (« Codes du milieu +2 : s'applique ? »).
  • les jets fréquents (Perception, Esquive, attaque principale) doivent être des raccourcis épinglés plutôt qu'un sélecteur de 25 compétences.
  • la Difficulté visée n'est pas toujours connue du joueur ; afficher la DR obtenue pour chaque seuil (12/15/18/21/25) au lieu d'un total brut aide le MJ à trancher vite.
